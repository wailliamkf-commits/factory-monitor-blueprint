# 九路厂区监控：厂家接入资料清单

日期：2026-09-26  
范围：接口与部署前资料研究；没有真实源地址、账号或现场视频，本文件不构成接入成功、实时性、识别效果或算力验收证据。

## 结论

先确认视频实际由哪台设备提供：摄像机直出，或 NVR/DVR 汇聚后按通道输出。Seetong 客户端/平台名称不能代替摄像机或录像机的制造商、型号和固件信息；请分别列出客户端、摄像机、NVR及其责任厂家。Frigate 的摄像机向导也会探测并返回设备制造商、型号、固件、媒体配置数量和 RTSP 候选地址，说明识别接入端设备与客户端品牌是不同事项。[Frigate 摄像机配置](https://docs.frigate.video/configuration/cameras/)

优先评估“每路低码率子码流用于常驻检测、主码流用于录像/事件复核”的组合。Frigate 支持给同一摄像机的输入分配 `detect` 与 `record` 角色，并明确举例将子码流用于检测、主码流用于录像；但每台设备是否有两个可用码流、是否允许并发拉取及其规格，必须由对应型号/固件资料和现场测试确认。[Frigate 摄像机配置](https://docs.frigate.video/configuration/cameras/) [Frigate 入门：录像配置](https://docs.frigate.video/guides/getting_started/)

新采购或换代时优先询问 Profile T；ONVIF 已宣布 Profile S 新产品/新固件合规提交将于 2027-03-31 截止，现有 S 设备仍可继续用于基本视频流，最终以准确型号和固件的官方登记为准。[ONVIF Profile S](https://www.onvif.org/profiles/profile-s/) [Profile S 退役问答](https://www.onvif.org/profiles/profile-s/profile-s-deprecation-qna/)

## RTSP为何值得优先核查

若相机/NVR在厂区局域网内向经授权的只读账号开放RTSP，推理主机可直接读取设备编码流，绕过“桌面截取 Seetong 播放窗口”这一环节。这样可以避免窗口遮挡、客户端布局/缩放和桌面采集权限影响输入帧，也可按设备提供的主/子码流分别选择检测与复核画质；Frigate/go2rtc的RTSP restream能够将一条上游连接供检测、录像或实时查看复用，并直接转发原流而不重新编码。[Frigate Restream](https://docs.frigate.video/configuration/restream/) [go2rtc RTSP](https://github.com/AlexxIT/go2rtc/blob/master/internal/rtsp/README.md)

这并不绕过设备授权，也不保证一定更清晰：如果设备/NVR只允许低清流、只开放客户端私有协议、并发连接额度已满、跨VLAN不通，或RTSP账号无相应通道权限，直连方案仍不可用。Seetong客户端播放的设备来源、画面清晰度和权限边界都须由厂家/现场管理员确认。RTSP“可播放”也不能代替新鲜像素、时间戳和帧完整性验证。

## 平台和验收边界

目标“RTX 4060 8GB、九路常驻轻量检测、事件触发高分辨率复核”目前是待测配置，显存容量或流接通本身不证明九路持续解码、检测队列及时或并发复核达标。Frigate规划指南把6–12路且部分活动重叠列为中等并发活动负荷，并要求核实GPU可支持的并发视频流数量；这只能说明九路负载需要实测，不能证明4060达标。取得实际码流参数、并发连接/带宽限制和录像方式后，再在目标主机测解码、检测帧率、队列延迟、丢帧、显存与CPU占用、九路同时事件复核及持续运行。Frigate官方安装说明指出其最佳运行环境是裸机Debian系Linux；Windows并非官方支持平台，在WSL/虚拟机下GPU设备透传可能困难或无法实现。因此，当前Mac上的文档研究或预演不能代替最终Windows设备验收。若选择Frigate，应优先评估其受支持的Linux部署；若延续本项目的Windows原生服务，则单独开发/验证解码与推理后端，不需要因此引入WSL硬件透传。[Frigate安装与OS说明](https://docs.frigate.video/frigate/installation/) [Frigate规划指南](https://docs.frigate.video/frigate/planning_setup/)

## 无标准流时的补充问题

这些是向具体厂家提出的能力询问，不表示设备已支持：

- 是否有官方 SDK 或本地视频接口？请提供开发文档、示例、支持的 Windows x64 / macOS arm64 / Linux 平台、认证和重连流程、错误码、通道映射、主/子流选择及授权/再分发条件。
- 如果只能使用 Seetong，请提供实际客户端版本、本地登录或云/P2P模式；确认是否有官方本地转流入口、独立详情窗口、主码流切换方式，以及后台/遮挡后的渲染行为。云设备编号本身不能当作 RTSP 地址。
- 如果摄像头接在 NVR 内部 PoE 网段，请确认 NVR 对外逐通道转发能力，或由现场管理员安排受控路由；不能假设接到厂区网络的电脑可直接访问内部摄像头。
- 如果设备已有智能告警，请给实际支持的事件类型、摄像头/通道ID、时间、框/区域、置信度（若有）及订阅接口；先做独立漏报核验，不能把厂商事件作为唯一分析触发条件。

## 可以直接发给厂家/集成商

我们计划在厂区局域网内增加九路本地视频分析，不改变原有录像与 Seetong 观看流程。请先协助验证一个通道，并提供：

1. 录像机及摄像头的品牌、完整型号、固件，九路通道编号与现场位置对应关系。
2. 录像机对外逐通道输出的主/子码流获取方法；若无此功能，请说明能否直接访问摄像头 RTSP，或提供官方 SDK。请给准确接口文档及一路验证结果。
3. 每路编码、分辨率、帧率、平均/峰值码率、GOP间隔、时间同步方式，以及主/子码流是否同视野、如何对齐时间。
4. 在原录像和 Seetong 仍运行时，是否支持新增九路主流与九路子流访问；请列总出流带宽、每通道/每账号并发连接和回放限制。
5. 测试电脑接入的网段、必要端口、NVR内部PoE网段是否可达；请在现场建立仅有预览和必要回放权限的账号，口令通过现场受控方式配置，不写入公开文档。
6. 高清录像按通道、起止时间检索、回放和下载的方法，以及新录像片段多久可读取；如有人员/越线等AI事件接口也请附说明。

暂时无法回答的项请明确标“未确认”或“不支持”。第一步只需确认一路可用的取流方法和上述设备/容量信息，再扩展到三路及九路测试。

本次没有厂商资料、设备型号、真实流地址或网络访问权限；没有读取或上传私有视频，也没有构造RTSP URL、用户名或口令。下步应先向集成商索取上表“必需”字段和九路通道映射，再安排经授权的单路只读连通性试验。
